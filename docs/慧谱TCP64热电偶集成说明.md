# 慧谱 TCP64 热电偶通信与采集

本系统通过串口 Modbus RTU 读取慧谱 TCP64 的 64 路温度，按 CH1～CH64 映射到 `温度1`～`温度64`，并使用现有连续 8 路分组、原始数据保存和均值派生规则。驱动标识为 `huipu_tc64_modbus_rtu`，采集方案为 `new_collection_v13_0`。

TCP8–TCP64 是仪表型号系列。配套协议描述的是串口 Modbus RTU，不能据型号名称选择 Modbus TCP 或 PLC 驱动。商家上位机的 PC 私有通信模式与这里的 Modbus 模式需要在仪表上明确切换；本驱动不实现未公开的 PC 私有报文。

参考 C# 程序位于 `D:\software\上位机\本机上机调试资料包-20260909\02-源程序\2-源码\运行版-无硬件模拟`。热电偶服务使用真实串口和逐通道 FC03 请求；其默认 COM2 不是设备身份。源码及附带日志用于协议回归，不能代替当前 USB 实物验证。逐通道与批量请求范围不同，不能仅凭该差异认定通信故障根因。

## 仪表连接设置

1. 在仪表系统设置中选择 **Modbus 通信**，设置非零仪表地址；系统默认地址为 1，必须与仪表一致。
2. 使用仪表通信接口接入电脑，选择实际枚举出的 COM 口。协议说明指定仪表内部通信 1 端口的 RS232；说明书另列 RS485、USB 通信方式，具体端口可用性取决于实物。前部 USB 的 U 盘导出模式不等于串口采集。
3. 默认串口参数为 **115200、8 数据位、无校验、1 停止位、无流控**。说明书也列出 2400、4800、9600、19200；修改时仪表和系统必须一致。
4. 退出商家软件对同一串口的占用。在系统中选择“慧谱TCP64热电偶（64路 Modbus RTU）”，绑定物理串口，填写仪表地址，选择需要保存的温度通道后进行接口检查。

系统只发送 FC03 读取命令，不写仪表参数，不自动修改通道开关、传感器类型、温度补偿、报警上下限或通信模式。仪表侧需要启用实际使用的通道并设置正确探头类型。

页面和 Helper 将串口列为传输候选；CH340/FTDI、COM 排序或 USB 位置不能单独确认 TCP64。首次绑定需要人工选择实际接口，可用单独拔插前后的枚举变化确认对应。多候选不自动分配热电偶；重新发现保留停用状态及离线手动绑定，不能占用其他角色端口。具有唯一稳定序列号时可定位同一设备的新端点，端点或位置变化后需要重新验证；没有稳定身份的设备断开后要求重新选择并检查。

驱动“读取方式”默认 `channel_temperature`，可显式选择 `full_record_block`；现场 local_direct 和 remote_helper 配置模板显式选择已验证的完整记录批量方式，需与实际仪表兼容。失败时不会自动切换。页面提供单请求超时、新鲜度和重连窗口设置，保存方案会保留这些参数、设备身份及通道设置，但不会保存可跨软件会话复用的采集就绪授权。同一软件会话内，正常停止和再次采集复用检测结果；配置变化、设备故障、断线或软件重启使相应授权失效。配置文件加载、本机及 Helper 使用同一配置规范化和驱动工厂。缺少读取方式的旧方案迁移为逐通道方式，必须重新检查；非法方式拒绝。端点、身份、地址、波特率、启用状态、读取方式及通道设置变化均使旧检查失效。

## 报文与寄存器

请求为 `地址 03 起始地址高 起始地址低 数量高 数量低 CRC低 CRC高`。寄存器地址从 0 开始，单次最多读取 125 个寄存器；响应字节数等于寄存器数的两倍，每个寄存器内部高字节在前。

协议手册的读取示例：

```text
请求：01 03 00 00 00 04 44 09
响应：01 03 08 00 01 00 00 00 08 00 02 85 14
```

通道 n 的记录起始地址为 `(n - 1) × 20`，每路占 20 个寄存器。

| 通道内偏移 | 含义 |
| --- | --- |
| 0 | 采样速度：2 低速、1 中速、0 高速 |
| 1 | 单位：0 摄氏度、1 开尔文、2 华氏度；其他编号为非温度单位 |
| 2 | 输入类型：0～7 为 K/S/R/N/E/J/T/B 热电偶，8～10 为 PT100/PT1000/Cu50；其他编号为流量、压力、电流或电压 |
| 3 | 显示小数位数；温度值本身为 float32，不按该字段再次缩放 |
| 4～11 | 上上限、上限、下限、下下限，各两个寄存器 |
| 12～13 | 温度补偿值 |
| 14 | 通道开关：0 开、1 关 |
| 15～17 | 预留 |
| 18～19 | 只读温度 float32，低 16 位字在前、高 16 位字在后 |

CH1 温度地址为 18、19（`0x0012`、`0x0013`）；CH64 为 1278、1279（`0x04FE`、`0x04FF`）。温度不是紧密排列的连续 128 个寄存器。协议的 float32 示例为 `E6 66 42 F6`，重排为 `42 F6 E6 66` 后约为 123.45。

默认逐通道方式按 CH1～CH64 顺序读取 `18 + (CH - 1) × 20` 起始的 2 个温度寄存器，正常响应 9 字节，每轮 64 个温度事务。CH1 请求 `01 03 00 12 00 02 64 0E`，响应样例 `01 03 04 64 2B 41 FB E4 D8` 解码约为 31.424°C，内部保留 float32 精度，不强制三位舍入。

逐通道方式在连接首轮以小范围 FC03 查询偏移 1～2 的单位及输入类型、偏移 14 的开关，再读取 64 路温度，完整支持时首轮共 192 个事务。首轮整体验证通过后，本连接后续每轮复用已验证的设置，只发送 64 个温度请求；关闭、重连或配置变化会清除设置缓存并重新验证。该方式不发送 120 寄存器温度请求。完整记录批量方式每次读取 6 路的 120 个寄存器，前 10 次起始地址为 0、120、…、1080，最后读取 1200 起始的 80 个寄存器，共 11 次请求。两种方式都检查地址、功能码、长度和 CRC16，保留帧间静默，支持分片及 5/6 字节异常帧；附加数据和跨请求残留帧会被拒绝。串口读取采用非阻塞方式，单请求截止和完整帧后的静默窗口由高分辨率单调时钟控制，不为每个合法短响应额外等待通用串口读取超时。

设置来源在检查结果中显示为仪表读回、操作者确认或未确认。只有仪表明确以不支持功能、数量或地址的异常响应拒绝设置查询时，才可使用人工设置：在“逐通道设置JSON”填写 `{"channels":{"温度1":{"unit":0,"input_type":0,"switch":0}}}`，为每个需确认的通道填写实际值，然后点击“已核对仪表当前通道设置”，再检查设备。`unit` 为 0摄氏/1开尔文/2华氏，`input_type` 为协议输入类型编号，`switch` 为 0开/1关。未填写的通道保持未确认，不能默认有效。确认绑定到实际端点、身份、波特率、地址及读取方式；改变这些条件或重连后须复核。无响应、CRC 错误不能通过人工确认绕过。

## 系统数据与质量

- `温度1`～`温度64` 保存摄氏温度。开尔文减 273.15，华氏度按 `(F - 32) × 5 / 9` 转换；不会重复做热电偶电压换算或叠加冷端补偿。
- 通道关闭、开关状态异常、非温度输入、非温度单位、NaN 或无穷值均发布为空值和无效质量。其他有效通道正常保留。通道原因位于 `channel_errors`。
- 一轮所有请求校验通过后，才发布该轮 64 路值；CH1 无效仍继续读取后续通道。任一温度事务超时或校验失败时整轮废弃，不混用新旧数据。全轮均无有效温度时，协议有效与温度无效分别报告。
- `温度1`～`温度8` 为 TC-G01，依此类推，`温度57`～`温度64` 为 TC-G08。每组均值要求 8 个有效成员；缺失不会直接当作 0。整层缺失的派生补值继续遵守系统既有规则，原始采集不写入补值。
- 系统可选取通道子集保存，但设备读取仍覆盖全部 64 路，用于保持通道编号及配置检查一致。
- 本机与 Helper 远程采集共用该驱动、通道名、质量状态和统一帧格式。CSV、MySQL 和界面不增加另一套温度通道。
- 时间戳来自主机完成扫描时刻。协议没有设备时间戳或采样序号，不能据一次软件快照宣称 64 路在同一硬件时刻采样。
- 仪表说明书的内部记录间隔不等于完整扫描速度。启动及整轮截止预算覆盖所选方式的事务数、请求超时、线速和帧间间隔；停止可取消后续事务并释放串口。系统记录扫描起止、耗时和完成接收时刻。每轮结束后才安排下一轮，默认最小轮询间隔 0.1 秒。TCP64 有效新鲜度取配置值与 `2.5 × 实测扫描耗时 + 轮询间隔` 的较大值；每轮完整扫描才增加观测序号，期间为保持值，超期为空值。界面刷新不能视为新硬件采样。

## 异常与实机核验

协议列出的异常功能码为 `0x83` 和 `0x86`，异常号为 `0x0205`（CRC 错误）、`0x0206`（寄存器数量超出）、`0x0209`（不支持的功能号）、`0x0210`（越界地址）。驱动支持带两个异常数据字节的厂商读异常，也识别标准 Modbus 的单字节异常，并保留错误编号。地址不匹配时仪表不响应，可能表现为超时。

协议没有明确给出探头断线、超量程等故障对应的有限数值哨兵，也没有独立冷端温度寄存器。驱动不会猜测有限数值哨兵；探头断线时若仪表输出有限数值，仅凭该协议尚不能识别为故障。通道断线行为和冷端补偿效果必须实机核对。

连接检查和采集诊断包含实际端点、地址、波特率、读取方式、寄存器范围、累计 TX/RX 字节数、最后有界原始帧、扫描耗时及错误分类。串口可打开但 RX 为零属于协议未验证，需核对通信模式、地址和 USB 通路；端口占用须退出占用软件后重查，不主动关闭未知进程。真实采集会话运行时拒绝临时探针。物理发现、协议有效和有效温度分别呈现，旧 HID 枚举不代表 TCP64 可达。

TCP64 默认恢复窗口为 60 秒，可配置 0～300 秒；已取得观测的会话不会因五次快速重试就过早结束恢复。每次重连先关闭旧串口，再创建新对象并按稳定身份定位，完整重验后才能发布温度。缺少稳定身份时报告绑定待确认，避免打开同 COM 号上的其他设备；重新选择及检查后开始新会话。人工通道设置不直接继承到恢复后的连接。

实机核验应逐路或逐组施加可识别温度变化，对照商家软件与仪表显示，特别核对 CH1、CH8、CH9、CH56、CH57、CH64；然后检查单探头拔出、通道关闭、串口断开和重新连接。两套软件需要依次使用串口及各自要求的通信模式。最后对照原始 CSV、MySQL、界面编号和 8 组均值。软件协议仿真不构成硬件验收证据，`hardware_facts` 用于独立记录铭牌、接线、采样率、量程、补偿和故障码等实机事实。`pre_sensor` 正式部署模板校验仍要求这些验收资料完整；界面协议连接检查使用实际串口读回与既有 Readiness 检查。
