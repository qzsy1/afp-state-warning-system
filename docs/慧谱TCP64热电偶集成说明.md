# 慧谱 TCP64 热电偶通信与采集

本系统通过串口 Modbus RTU 读取慧谱 TCP64 的 64 路温度，按 CH1～CH64 映射到 `温度1`～`温度64`，并使用现有连续 8 路分组、原始数据保存和均值派生规则。驱动标识为 `huipu_tc64_modbus_rtu`，采集方案为 `new_collection_v13_0`。

## 资料与适用范围

资料目录为 `D:\keti\自动铺丝\数据采集相关`。

| 资料 | 内容和使用范围 |
| --- | --- |
| 热电偶采集仪协议.pdf | 《多路温度记录仪 Modbus 通讯协议》，TCP8–TCP64，2021/08/02，A 版；串口参数、FC03/FC06、寄存器布局、字序、CRC 和异常码依据 |
| （常规）5寸40-64多功能TCP多路温度记录仪说明书慧谱(1).docx 及同名 (1)(1) 文件 | 仪表接线、PC/Modbus 通信模式、温度单位、输入类型、串口参数及上位机操作说明 |
| HpTemperatureLogger_CN_V1.2.zip | 商家上位机安装包；内含安装 EXE，主程序为 Qt `TemperatureLogger.exe`，不含程序源码或独立的通信开发接口 |
| USB下载口驱动程序CH340.exe | USB 串口相关驱动安装程序；是否适用应以实际接入后设备管理器识别结果为准 |

TCP8–TCP64 是仪表型号系列。配套协议描述的是串口 Modbus RTU，不能据型号名称选择 Modbus TCP 或 PLC 驱动。商家上位机的 PC 私有通信模式与这里的 Modbus 模式需要在仪表上明确切换；本驱动不实现未公开的 PC 私有报文。

## 仪表连接设置

1. 在仪表系统设置中选择 **Modbus 通信**，设置非零仪表地址；系统默认地址为 1，必须与仪表一致。
2. 使用仪表通信接口接入电脑，选择实际枚举出的 COM 口。协议说明指定仪表内部通信 1 端口的 RS232；说明书另列 RS485、USB 通信方式，具体端口可用性取决于实物。前部 USB 的 U 盘导出模式不等于串口采集。
3. 默认串口参数为 **115200、8 数据位、无校验、1 停止位、无流控**。说明书也列出 2400、4800、9600、19200；修改时仪表和系统必须一致。
4. 退出商家软件对同一串口的占用。在系统中选择“慧谱TCP64热电偶（64路 Modbus RTU）”，绑定物理串口，填写仪表地址，选择需要保存的温度通道后进行接口检查。

系统只发送 FC03 读取命令，不写仪表参数，不自动修改通道开关、传感器类型、温度补偿、报警上下限或通信模式。仪表侧需要启用实际使用的通道并设置正确探头类型。

## 报文与寄存器

请求为 `地址 03 起始地址高 起始地址低 数量高 数量低 CRC低 CRC高`。寄存器地址从 0 开始，单次最多读取 125 个寄存器；响应字节数等于寄存器数的两倍，每个寄存器内部高字节在前。

协议手册的读取示例：

```text
请求：01 03 00 00 00 04 44 09
响应：01 03 08 00 01 00 00 00 08 00 02 85 14
```

通道 n 的记录起始地址为 `(n - 1) × 20`，每路占 20 个寄存器。

| 通道内偏移 | 含义 |
| --- | --- |
| 0 | 采样速度：2 低速、1 中速、0 高速 |
| 1 | 单位：0 摄氏度、1 开尔文、2 华氏度；其他编号为非温度单位 |
| 2 | 输入类型：0～7 为 K/S/R/N/E/J/T/B 热电偶，8～10 为 PT100/PT1000/Cu50；其他编号为流量、压力、电流或电压 |
| 3 | 显示小数位数；温度值本身为 float32，不按该字段再次缩放 |
| 4～11 | 上上限、上限、下限、下下限，各两个寄存器 |
| 12～13 | 温度补偿值 |
| 14 | 通道开关：0 开、1 关 |
| 15～17 | 预留 |
| 18～19 | 只读温度 float32，低 16 位字在前、高 16 位字在后 |

CH1 温度地址为 18、19（`0x0012`、`0x0013`）；CH64 为 1278、1279（`0x04FE`、`0x04FF`）。温度不是紧密排列的连续 128 个寄存器。协议的 float32 示例为 `E6 66 42 F6`，重排为 `42 F6 E6 66` 后约为 123.45。

驱动每次读取 6 路的完整记录，即 120 个寄存器；前 10 次起始地址为 0、120、240、…、1080，最后读取起始地址 1200 的 80 个寄存器，覆盖 CH61～CH64。共 11 次请求；每次均检查地址、功能码、长度和 CRC16，保留串口静默间隔并累计分片数据。

## 系统数据与质量

- `温度1`～`温度64` 保存摄氏温度。开尔文减 273.15，华氏度按 `(F - 32) × 5 / 9` 转换；不会重复做热电偶电压换算或叠加冷端补偿。
- 通道关闭、开关状态异常、非温度输入、非温度单位、NaN 或无穷值均发布为空值和无效质量。其他有效通道正常保留。通道原因位于 `channel_errors`。
- 一轮的 11 个响应全部校验通过后，才交给采集线程发布该轮 64 路值。任一报文超时或校验失败时不发布该轮部分结果，由现有采集线程执行关闭和重连。
- `温度1`～`温度8` 为 TC-G01，依此类推，`温度57`～`温度64` 为 TC-G08。每组均值要求 8 个有效成员；缺失不会直接当作 0。整层缺失的派生补值继续遵守系统既有规则，原始采集不写入补值。
- 系统可选取通道子集保存，但设备读取仍覆盖全部 64 路，用于保持通道编号及配置检查一致。
- 本机与 Helper 远程采集共用该驱动、通道名、质量状态和统一帧格式。CSV、MySQL 和界面不增加另一套温度通道。
- 时间戳来自主机完成扫描时刻。协议没有设备时间戳或采样序号，不能据一次软件快照宣称 64 路在同一硬件时刻采样。
- 仪表说明书的内部记录间隔不等于 Modbus 的全通道读取速度。仅 11 个响应的总长度已为 2615 字节，115200-8N1 的理论响应传输时间约 0.227 秒，另需请求、静默间隔和设备处理时间。系统记录 `scan_duration_seconds`；默认新鲜度为 1 秒，低速串口应据实测扫描时长调大 `freshness_seconds`。统一帧频率高于设备刷新频率时，应通过现有质量字段识别保持值。

## 异常与实机核验

协议列出的异常功能码为 `0x83` 和 `0x86`，异常号为 `0x0205`（CRC 错误）、`0x0206`（寄存器数量超出）、`0x0209`（不支持的功能号）、`0x0210`（越界地址）。驱动支持带两个异常数据字节的厂商读异常，也识别标准 Modbus 的单字节异常，并保留错误编号。地址不匹配时仪表不响应，可能表现为超时。

协议没有明确给出探头断线、超量程等故障对应的有限数值哨兵，也没有独立冷端温度寄存器。驱动不会猜测有限数值哨兵；探头断线时若仪表输出有限数值，仅凭该协议尚不能识别为故障。通道断线行为和冷端补偿效果必须实机核对。

实机核验应逐路或逐组施加可识别温度变化，对照商家软件与仪表显示，特别核对 CH1、CH8、CH9、CH56、CH57、CH64；然后检查单探头拔出、通道关闭、串口断开和重新连接。两套软件需要依次使用串口及各自要求的通信模式。最后对照原始 CSV、MySQL、界面编号和 8 组均值。软件协议仿真不构成硬件验收证据，`hardware_facts` 用于独立记录铭牌、接线、采样率、量程、补偿和故障码等实机事实。`pre_sensor` 正式部署模板校验仍要求这些验收资料完整；界面协议连接检查使用实际串口读回与既有 Readiness 检查。
