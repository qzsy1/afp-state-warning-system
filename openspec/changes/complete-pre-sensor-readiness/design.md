# Design

## Context

参见 [proposal.md](proposal.md) 的动机及本变更四个 delta spec。当前 `main@2047f35` 已有双模式共享采集核心、readiness 快照、统一帧、ACK/重传、异步写入、journal 和 MySQL retry spool；Harness 单元/合同基线为 128/128，quick 为 9/9。本轮不得重新实现这些能力，而要把它们组织成可安装、可预检、可演练、可审计的现场候选。

现状中存在三个必须正面处理的结构问题：应用版本、Helper 构建号和模块启动器版本分别硬编码；现有 `real_acquisition_preflight.py` 主要验证权威源、候选摘要和导入，尚不是完整环境预检；现有矩阵把真实传感器、第二台电脑和目标 MySQL 都作为 field 项，无法表达“物理设备待验收”与“环境阻塞”的区别。

实现约束：

- 产品事实来源仍是 `visualization_app/`，装配仍由 `modular_runtime/` 完成，Harness 负责门禁与证据；正式 `delivery/` 不得被写入。
- `local_direct` 与 `remote_helper` 继续复用同一统一帧、质量、持久化和停止核心。
- 所有产品行为先有针对缺失合同的 RED，再做最小 GREEN；配置和纯文档不伪造行为测试。
- 密码、Token、数据库凭据、设备私有路径和机器秘密不得进入模板、manifest、报告或证据包。
- 对目标 MySQL、第二台电脑、管理员权限和生产网络的缺失必须报告 `blocked`，不得转写为传感器待验证。

## Goals / Non-Goals

**Goals:**

- 从同一发行合同派生主程序、Helper、配置 schema、静态资源和协议身份，并在启动副作用前失败关闭。
- 提供可复现的候选装配、统一预检、双模式故障演练、环境阻塞分类和脱敏证据链。
- 让第二台电脑和目标 MySQL 可用时能够直接执行真实环境验证，不可用时仍完成全部仓库内及本机协议模拟工作。
- 让最终剩余清单通过机器门禁保证只包含真实设备物理特性。

**Non-Goals:**

- 不改变双模式共享采集核心的职责边界，不增加第三种真实采集模式。
- 不替代真实传感器校准、通道完整性、现场电磁/USB 负载或实物耐久验收。
- 不自动变更生产防火墙、电源策略、网卡设置、系统时间策略、正式 MySQL 权限或正式 `delivery/`。
- 不伪造模型、历史数据、预警证据或生产预测批准来掩盖回归失败。确需恢复派生测试产物时，只能使用仓库声明的权威输入与生成器，并记录可复现命令、输入摘要和输出摘要；不得从正式 `2.0.4` delivery 复制产物冒充 `2.0.5` 来源。

## Decisions

### 1. 使用一个源发行合同和一个候选manifest

在装配源中维护不含机器状态的版本化发行合同，声明应用版本、Helper 协议、统一帧合同、配置 schema 和最低能力集合。装配时生成候选根目录的 `RELEASE-MANIFEST.json`，加入 Git 修订、候选 ID、受管文件和静态资源摘要；`SHA256SUMS.txt` 继续承担逐文件完整性。主程序和 Helper 通过同一个轻量加载器读取该合同，开发态也必须解析同一源文件。

选择这一方案而不是继续同步多个常量，因为多常量无法证明来自同一修订；也不把 `SHA256SUMS.txt` 单独当版本合同，因为摘要文件不表达协议和配置兼容性。动态 `built_at` 不参与兼容判断，候选 ID 与内容摘要才是稳定身份。

### 2. 把模式模板设为唯一可分发配置起点

在权威源中维护 `local_direct` 与 `remote_helper` 两份 JSON 模板，共享公共字段但不通过运行时继承合并，以便操作员看到完整有效配置。模板使用占位标识或环境引用表示秘密，禁止出现真实值。一个 schema 校验器先做结构、范围、通道/单位和模式互斥检查，再构造现有 `AcquisitionConfig` 做语义检查。

选择完整模板而不是一个含条件分支的大模板，因为现场编辑时模式专属字段更容易误留。兼容旧 API 的默认行为保留，但现场正式入口只接受显式模板 schema。

### 3. 统一预检采用可组合探针和严格状态聚合

新增预检编排器，探针返回同一结构：`check_id`、`status`、`summary`、`evidence`、`remediation`、`evidence_level`、`requires_external_environment`。聚合器只接受 `passed`、`failed`、`blocked`、`physical_sensor_pending`，并在 JSON schema 层限制只有白名单设备读取 ID 可使用最后一种状态。人类报告由同一结果对象渲染，避免两种报告漂移。

探针分组为候选身份、运行环境、配置、存储、MySQL、Helper/网络、Windows 策略、容量/恢复。各探针是只读或使用自清理事务：存储探针执行创建、写入、关闭、重命名、删除；MySQL 使用唯一探针事务并回滚；网络只连接声明端口；Windows 探针只读取状态。权限不足是 `blocked`，确定不合规是 `failed`。

选择模块化探针而不是扩展一个巨型脚本，便于单项 TDD、超时隔离和第二台电脑复用；PowerShell 入口只负责参数、权限上下文和调用 Python/候选可执行文件。

### 4. 环境证据与物理设备证据分开建模

Harness 增加环境阻塞和物理待验收的独立需求族。第二台电脑、目标 MySQL、管理员权限和生产网络均带 `requires_external_environment=true`；缺失时是 `blocked`，不会让仓库内自动测试失败，但会阻止“全部传感器前准备完成”的总结果。只有设备身份/端口对应、真实通道值和真实驱动生命周期可为 `physical_sensor_pending`。

选择显式阻塞而不是继续使用统一 `field_pending`，因为后者会把可在无传感器条件下完成的环境准备错误推迟到现场。

### 5. 耐久演练复用生产边界并以故障适配器注入异常

演练器直接调用现有 `AcquisitionManager`、本地适配器、Helper 调度器、远程镜像、journal 和 MySQL 协调器。故障只在外部边界注入：模拟驱动时钟、受控慢写目标、可断开的数据库适配器、短生命周期 HTTP/WebSocket 服务和可重启 Helper 进程。不得复制统一帧、ACK、重传或停止逻辑到测试实现。

CLI 默认每种模式 1800 秒、10 Hz；单元测试显式传入短持续时间并标注 `short_automated`。演练报告记录目标/实际帧、绝对序号、质量、各持久介质计数、队列和磁盘峰值。目标 MySQL 或真实第二台电脑不可用时，相应结果保持 `blocked`，本机 fake 只获得 `automated` 或 `protocol_simulation` 等级。

### 6. journal、日志和spool共享容量策略

定义统一容量策略字段：软告警阈值、硬上限、最小剩余磁盘、轮转/拒绝策略和保留条件。现有异步写入队列、服务器 journal 与 retry spool 继续各自存储，但向同一容量检查接口报告当前字节数、峰值和状态。硬上限前告警；达到上限时按数据完整性优先失败关闭，不静默丢弃正式帧。

选择共享策略和状态接口而不是合并物理存储，避免扩大现有可靠性核心的改动面。

### 7. 候选、双机脚本和证据使用可搬运目录

候选输出默认位于被 Git 忽略的 `artifacts/pre-sensor-candidates/<candidate-id>/`，绝不位于 `delivery/`。候选包含模板、预检入口、Helper、现场脚本、手册和真实设备剩余清单。第二台电脑脚本只需要候选目录和非秘密参数；其输出为可拷回主机的证据目录。

证据导出器生成文件清单和摘要，并对文件名、JSON 键值、环境变量形式、URL 用户信息和已知密钥模式做扫描/脱敏。发现无法安全脱敏的秘密时失败关闭。正式发布仍是独立动作，需要用户另行授权。

候选替换采用“先新增、后验证、最后清理”的生命周期。修正版候选必须装配到新的唯一目录，禁止覆盖、合并或就地修补既有候选。只有新候选的发行身份、所有受管摘要、主程序与 Helper、隔离自检、所需回归及候选前后摘要均通过，且旧候选未被进程、计划任务、服务、watchdog 或当前证据步骤引用时，旧候选才可认定为不再需要。删除前把旧候选路径、候选 ID、manifest、摘要、删除理由和新候选通过证据写入指定证据目录；删除后验证目标不存在、新候选仍完整、正式 `delivery/` 与证据目录未改变。任何门禁失败时保留所有候选并报告阻塞。

### 8. Harness先于软件扩展并保存RED→GREEN证据

先为新需求 ID、状态分类、模板、版本不一致、候选验证、预检聚合、环境阻塞、演练和证据边界写失败合同；每个测试运行的命令、失败原因和后续通过结果记录到变更证据报告。随后才修改 Harness 矩阵和软件。单元测试断言可观察结果，不以搜索源码文字代替执行行为。

选择分行为的小批次 TDD，而不是最后集中补测试，以便明确区分现有能力和本轮新增合同。

## Risks / Trade-offs

- [完整 Windows 设置读取在非管理员账户下不总可用] → 将权限不足建模为 `blocked`，提供只读提升权限脚本和人工复核命令，不自动改设置。
- [候选 manifest 同时包含内容摘要会产生自引用] → manifest 不包含自身和 `SHA256SUMS.txt` 的摘要；两者分别由校验器验证结构与受管内容集合。
- [30 分钟双模式演练耗时至少一小时] → 保留真实默认时长作为交付证据；窄测试使用显式短时参数，但报告不可升级为长时证据。
- [真实 MySQL 回滚权限与业务写入权限可能不同] → 分开报告连接、schema、权限、写入、回滚阶段；任一阶段失败均不合并为“连接失败”。
- [网络故障注入可能影响开发机其他连接] → 本机演练仅控制自建临时服务或子进程，不修改系统路由、防火墙或物理网卡。
- [版本严格门禁会拒绝旧 Helper] → 旧 Helper 只保留已有工程兼容状态，现场正式入口必须使用候选内匹配 Helper。
- [日志/journal/spool硬上限可能提前终止采集] → 在软阈值提前告警并保留已写证据；数据不完整时宁可失败关闭，不形成伪完整结论。
- [现有 full 的模型/历史数据缺失仍会失败] → 精确列出既有检查 ID 和归因，不生成缺失产物，也不让其掩盖本轮真实采集检查结果。
- [旧候选清理误删当前运行版本或审计依据] → 删除前解析进程、计划任务、服务和 watchdog 引用，保存候选身份与摘要证据，只允许删除明确列出的候选根目录；正式 `delivery/`、源码仓库和证据目录始终排除。

## Migration Plan

1. 完成并严格校验本 OpenSpec；记录 `main@2047f35`、Harness 128/128 和 quick 9/9 基线。
2. 先扩展 Harness 合同和需求矩阵，逐项保存 RED 证据，再实现最小 GREEN。
3. 增加统一发行合同、模式模板和预检模型，并把门禁接到设备/Helper 启动之前。
4. 增加候选装配、双机检查、耐久故障演练、容量报告和脱敏证据导出。
5. 在新的唯一隔离候选中完成导入、自检、静态资源、主程序与 Helper、manifest 和摘要验证；执行两种模式短时集成及默认长时 10 Hz 演练。
6. 若第二台电脑或目标 MySQL 可用，执行目标环境脚本；否则保留 `blocked`，并交付可直接执行的脚本和说明。
7. 运行全部 Harness、相关回归、OpenSpec 严格校验、语法/导入和 `git diff --check`，对比正式 `delivery/` 前后摘要。
8. 只有所有非物理项目通过，才生成“仅剩真实设备验证清单”；正式发布由后续授权动作完成。
9. 新候选全部门禁通过后，导出被替代旧候选的身份、摘要和验证证据，确认没有运行时引用，再删除明确认定为不再需要的旧候选目录；随后复验新候选、正式 `delivery/` 和证据目录。新候选未通过时不得删除任何候选。

回滚只需停止使用新候选目录并恢复到先前候选；因为本变更不覆盖正式 `delivery/`，无需从准备流程回滚正式发布文件。运行中产生的 journal/spool 只有在完成对账或明确导出后才允许清理。
