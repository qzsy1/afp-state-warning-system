## Context

参见 `proposal.md` 的动机。当前源码在 `F:\new_AFP_exam\AFP-Readiness-Repo`，但可运行内容同时存在于仓库的版本化 `delivery`、F 盘候选目录以及 D 盘候选目录；当前 8770/8771 监听程序仍从 D 盘候选启动。构建入口 `pre_sensor/build-candidate.ps1` 默认永久写入 `artifacts\pre-sensor-candidates\<candidate-id>`，若干 watchdog 与 Helper 自启动脚本还回退到旧版本化 delivery 或旧工程根目录。

迁移必须继续满足既有安全约束：不泄露密码、Token、配对码或环境秘密；MySQL 密码只通过安全提示输入；未经逐项授权不停止 8770 监听者、不改启动项、不删目录；模拟验证不冒充真实传感器或完整双机验收。

## Goals / Non-Goals

**Goals:**

- 建立一个固定且可预测的运行根目录，并让所有运行入口使用同一解析规则。
- 将“候选”从长期目录变为一次部署内的临时状态，成功和失败都能清理。
- 在不保留第二套完整二进制的条件下提供可审计的 Git 重建回滚。
- 把首次迁移拆成可验证、可暂停且有明确审批门的阶段，旧程序在新程序验证前始终可恢复。
- 对删除目标做绝对路径、保护根、活动进程和启动引用检查。

**Non-Goals:**

- 不改变 AFP 业务协议、Helper 协议、统一帧合同、采集算法或 MySQL schema。
- 不自动生成配对码，不把 remote_helper 未配对归类为真实传感器待验证。
- 不更换公网域名，不自动重配 Tailscale Funnel、防火墙、Windows 服务或系统策略。
- 不承诺离线瞬时回滚；选择 Git 重建意味着回滚依赖源码、Git LFS 与构建环境，耗时高于保留完整旧二进制。
- 不在本变更的规划阶段执行进程切换、注册表修改或目录删除。

## Decisions

### 1. 固定三根目录

采用以下唯一受支持路径：

- 源码：`F:\new_AFP_exam\AFP-Readiness-Repo`
- 运行：`F:\new_AFP_exam\AFP_Integrated_System_Modular`
- 证据：`F:\new_AFP_exam\AFP-Main-Evidence`

临时装配使用 `F:\new_AFP_exam\.afp-staging\<deployment-id>`。源码和证据不是可执行部署，不违反“只保留一个可用版本”。所有新生成的持久内容必须位于这三个固定根之一；临时内容只允许位于 staging 根。

替代方案一是保留“当前 + 前一版本”两个运行目录，回滚最快但持续占用约 2.4 GiB。替代方案二是保存压缩二进制备份，空间较少但仍形成第二份发布载荷。两者都不符合用户确认的单一版本目标，因此选择固定运行目录 + Git 重建。

### 2. 构建与部署分离

`build-candidate.ps1` 保留候选身份和 manifest 生成能力，但默认输出改为 F 盘临时 staging，并返回结构化部署元数据。构建阶段只装配和验证，不覆盖运行目录。部署入口负责状态盘点、审批门、受控替换、启动及验证；两个阶段共享同一固定路径配置，避免脚本各自硬编码版本化目录。

候选 ID 仍保留在 manifest 和证据中用于追踪，但不再决定持久目录名。这样既保留审计身份，又避免每次生成 1.2 GiB 目录。

### 3. 统一路径合同

新增一个版本受控的路径合同文件，声明 `workspace_root`、`source_root`、`runtime_root`、`evidence_root` 和 `staging_root`。PowerShell 脚本从合同解析路径，并在写操作前使用规范化绝对路径进行包含关系检查。测试可以通过显式临时根覆盖合同，但生产默认值固定为 `F:\new_AFP_exam`。

watchdog 与 Helper 安装脚本优先使用脚本所在的固定运行目录；在源码环境运行时读取路径合同，不再回退到 `F:\AFP_Integrated_Modular_v2` 或带版本号的 delivery。安装或更新启动项仍属于独立审批操作。

### 4. 状态机式提升

一次部署按以下状态推进：

1. `inventoried`：只读记录监听者、运行路径、版本、公网入口、启动项与待迁移目录。
2. `staged`：在临时目录完成装配。
3. `verified`：manifest、版本合同、摘要、Helper、`--verify-files`、`--self-test` 和 `--module-status` 全部通过。
4. `approval_required`：输出精确的 PID、路径、影响、预计中断和回滚命令，等待明确授权。
5. `switched`：只停止已盘点的 AFP 进程，把已验证内容部署到固定运行目录并启动。
6. `service_verified`：验证 8770、8771、本机、局域网、公网、Funnel 源站和静态资源身份。
7. `evidence_migrated`：证据已复制、摘要核对和秘密扫描。
8. `cleanup_approved`：再次列出待删绝对路径及空间，等待删除授权。
9. `complete`：历史副本已精确删除，staging 已清理，唯一运行版本检查通过。

任何阶段失败都停止向后推进。`service_verified` 之前不得删除旧运行材料；`evidence_migrated` 之前不得删除 D 盘证据。

### 5. 目录替换与失败恢复

在首次迁移中，当前 D 盘运行目录本身充当切换前恢复来源，直到 F 盘运行版本完成服务验证。固定运行目录若尚不存在，可从已验证 staging 原子重命名到目标；若已存在，部署入口先验证它不是运行中的路径，再使用同一卷上的临时交换名进行替换。交换名只能存在于操作期间，并在成功或失败恢复后清理。

若新版本启动或服务验证失败，停止新进程、恢复切换前启动记录并重新启动原 D 盘程序。只有新版本验证通过后，才进入启动项修改、证据迁移和历史目录清理。

常规后续更新不保留旧二进制，因此切换前必须确认指定 Git 回滚引用和构建输入可用；不可用时部署被 blocked。

### 6. Git 重建回滚

每次成功部署的证据记录 source revision、工作树摘要、candidate ID、manifest 摘要、Git LFS 可用性以及构建工具检查结果。回滚从干净的指定 Git 提交或标签装配临时 staging，经过与新版本相同的验证和审批后替换固定运行目录。

工作树带未提交修改的候选可以部署，但在清理前必须把对应改动固化为可访问的提交或补丁摘要；否则“可重建回滚”条件不成立，清理被 blocked。默认推荐先提交已确认源码和 OpenSpec 变更，再执行最终部署。

### 7. 证据迁移与脱敏

证据迁移采用“复制 → 相对路径清单 → SHA-256 核对 → 秘密模式扫描 → 原目录删除审批”的顺序。扫描结果只记录文件和规则类型，不回显匹配值。检测到秘密、摘要不一致或无法读取时，原证据保留且迁移状态为 failed。

### 9. 测试策略

先以测试固定路径合同、临时 staging、失败清理、活动引用拒绝、审批门和回滚输入检查，再修改脚本。静态测试负责阻止旧硬编码路径回归；临时目录集成测试负责装配和清理；实际切换采用只读盘点证据、预切换验证和服务冒烟三层验证。真实系统状态修改不在单元测试中模拟为成功验收。

## Risks / Trade-offs

- [删除旧二进制后回滚较慢，且依赖 Git LFS/构建工具] → 清理前验证回滚引用和全部构建输入；缺失时阻止清理。
- [固定目录原地升级可能留下混合文件] → 只允许完整 staging 提升，禁止逐文件覆盖受管内容，并在启动前重新执行摘要验证。
- [当前 D 盘进程在迁移中被误停或无法恢复] → 审批前锁定 PID、可执行路径和命令行；仅停止该进程，并在新服务验证前保留原目录。
- [启动项仍指向被清理目录] → 清理前枚举 HKCU Run、计划任务和 watchdog 引用；存在引用时阻止删除。
- [证据中含秘密] → 先脱敏扫描且不回显匹配值；扫描失败时保留原件并停止删除。
- [磁盘空间不足以同时容纳 staging 与当前版本] → 装配前计算所需空间并至少保留当前版本与一个 staging 的峰值容量；不足时 blocked，而不是提前删除旧版本腾空间。
- [带未提交修改的运行版本无法由 Git 精确重建] → 最终清理前要求可访问提交，或保存经过摘要绑定的补丁；否则 blocked。

## Migration Plan

1. 实现路径合同、临时 staging 构建、部署状态机与保护性测试，不修改正在运行的系统状态。
2. 更新文档、watchdog、Helper 安装入口和回归矩阵；运行完整测试与 OpenSpec 校验。
3. 只读重新盘点当前 PID、8770/8771、可执行路径、候选身份、公网 URL、Funnel 源站、启动项、目录大小和证据清单。
4. 在 `F:\new_AFP_exam\.afp-staging` 构建最新交付，执行全部身份、摘要和可执行自检；失败则清理 staging 并停止。
5. 输出准确切换目标、影响、预计中断及“重新启动 D 盘原程序”的回滚方法，等待用户明确授权。
6. 只停止已确认的旧 AFP 进程，把 staging 提升到固定运行目录并启动；验证端口、本机、局域网、公网、Funnel 与静态资源身份。
7. 若验证失败，恢复旧 D 盘程序并保留全部目录；若成功，在单独授权后把启动项更新为固定 F 盘路径。
8. 复制 D 盘证据到固定证据目录，完成清单、SHA-256 和脱敏检查。
9. 重新列出每个待删绝对路径、活动引用、大小、影响和不可用时的 Git 重建回滚方法，等待明确清理授权。
10. 逐项删除已批准且通过保护检查的历史目录，清理 staging，复核固定运行目录是唯一受支持的完整运行版本并保存最终证据。

回滚分为两阶段：首次迁移清理前直接恢复 D 盘原程序；清理后或后续发布则从记录的 Git 引用重建 staging，再走相同审批与验证流程部署到固定目录。
