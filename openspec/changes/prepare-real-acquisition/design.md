# Design

## Context

参见 [proposal.md](proposal.md) 的动机。仓库已经具备真实设备检查、统一采样、远程 Helper、CSV/MySQL 保存和无硬件测试基础，本变更不是重建采集系统，而是在现场落地前明确两种并列采集模式、消除重复职责，并加固能够通过夹具、模拟设备、本机临时服务器和故障注入验证的风险。

实现必须遵守以下约束：

- 不直接修改、重新生成或覆盖正式 `delivery/`；所有装配验证只在隔离临时目录执行。
- 不覆盖工作区已有修改，不执行破坏性 Git 操作。
- 保持仿真、现有 10 Hz 正常采集、公开 API、前端字段、CSV/MySQL 和旧调用方兼容。
- 不包含模型预测、历史预警、Dashboard 因果指标、真实标签或生产预测审批。
- 每项 Harness 和软件行为先观察到针对缺失合同的失败测试，再做最小修改。
- 自动化只能证明软件合同或协议模拟；没有真实传感器或第二台 Windows 电脑时，相应现场结论必须保持 `field_pending`。

## Goals / Non-Goals

**Goals:**

- 将 `local_direct` 与 `remote_helper` 定义为显式、并列、不可混用的一等真实采集模式。
- 让两种模式只在设备访问或跨进程传输适配层不同，共享设备/通道定义、采样时钟、统一帧、质量、状态机、持久化和停止语义。
- 让保存、展示和后续消费者只接收规范化统一帧包络，不依赖帧来自本机还是 Helper。
- 将本机设备故障与远程网络/Helper 故障分别诊断，再映射到统一采集状态和逐通道质量。
- 用 Harness 锁定模式隔离、输出等价、现场证据边界及正式 `delivery` 不变性。

**Non-Goals:**

- 不重新实现已经存在且验证通过的真实采集能力。
- 不写入、覆盖、发布或重新生成正式 `delivery/`。
- 不宣称 PLC、ABB、SMRF、UVC、M3232 或跨两台 Windows 电脑的现场采集已验收。
- 不改变模型、预警、Dashboard 因果指标、真实标签或生产预测审批。
- 不顺带重构与采集模式边界无关的页面、训练或分析代码。

## Decisions

### 1. 共享采集核心与统一通道合同

真实采集配置新增独立的显式模式字段 `real_acquisition_mode`，只允许 `local_direct` 或 `remote_helper`。它与现有区分真实/模拟的 `acquisition_mode` 是两个正交维度：模拟路径保持兼容；当 `acquisition_mode=real` 时必须明确选择真实采集模式，禁止根据地址、端口、设备在线状态或 Helper 可用性推断模式。

共享核心是两种真实模式的唯一规范化入口，拥有以下职责：

- 设备、接口、通道、单位、缩放和通道映射定义；
- 单调统一采样时钟与绝对序号生成规则；
- `capture_uuid`、绝对 `frame_sequence`、帧时间及逐通道来源时间、年龄、数值、`is_new` 和质量；
- `measured_new`、`held_within_freshness`、`stale`、`missing`、`invalid` 与断线质量判定；
- 统一采集状态机、持久化输入、恢复边界和停止收尾语义。

模式适配层只产生共享核心定义的原始通道样本或已协商的统一帧，不得各自复制通道映射、单位、质量或保存逻辑。共享核心输出不可变统一帧包络；旧 `rows`、`timestamps` 和既有状态字段作为兼容投影保留，但不再是新链路的事实来源。

PLC Modbus TCP 解析也属于共享设备合同：读取严格遵循 MBAP 长度含 Unit ID 的定义，并验证事务 ID、协议 ID、Unit ID、功能码、异常响应、字节数和寄存器数量。任何不一致都失败关闭，不返回部分数据。

### 2. 本机直连模式

`local_direct` 适配层独立负责主程序所在电脑的驱动检查、设备打开、读取、单设备重连、关闭和设备专属诊断。它不得启动、探测或依赖 Helper、WebSocket、HTTP、远程 readiness 快照或远程能力协商。

每个设备档声明最小轮询间隔、单次超时、连续失败阈值和有上限退避。必需接口必须在正式启动阶段达到 opened/首帧门禁；检查后端口失效时启动明确失败。单设备异常不停止其他设备，但受影响通道由共享核心标记为缺失、陈旧或无效，状态同时保留本机驱动错误类别、尝试次数、退避和最后错误。

模式专属配置只允许本机驱动与设备连接字段。若同时提供 Helper 地址、远程会话或能力协商字段，配置必须以 `mode_field_conflict` 失败，不得静默忽略或切换模式。

### 3. 远程 Helper 模式

`remote_helper` 适配层独立负责跨进程 readiness 快照、Helper 命令、能力协商、WebSocket/HTTP、ACK、批量传输、断线重传和远程对账。主程序不得在该模式下直接打开远端传感器或绕过 Helper readiness。

隔离检查子进程返回可序列化 `ReadinessSnapshot`：规范化配置指纹、设备身份摘要、检查起止时间、有效期、接口结果、通道结果和 Helper 修订/能力。Helper 主进程在返回检查成功前把快照导入实际执行启动的采集代理；启动重新验证指纹、身份、时效和能力。秘密不得进入快照。WebSocket 与 HTTP fallback 复用同一导入、启动、停止和错误映射路径。

Helper 必须协商当前统一帧合同版本。正式模式不接受缺少 `capture_uuid`、绝对 `frame_sequence`、帧时间或逐通道质量的旧 Helper；显式工程降级可以继续，但持续标记 `production_conclusion_enabled=false`。批次按 `capture_uuid + frame_sequence` ACK；重传同内容幂等，同键不同内容失败，缺口保持可见且在完成对账前不得形成完整采集证据。

远程网络断线、Helper 进程故障、readiness 失效和能力不兼容分别诊断，再通过共享状态投影映射为受影响通道质量及采集降级/失败，不得伪装成本机设备故障。

### 4. 两种模式输出等价性

两种模式以相同设备/通道定义和相同输入样本运行时，经过规范化后必须产生字段、单位、质量和顺序等价的统一帧。允许不同的模式诊断元数据，但保存、展示和后续消费者使用的帧包络不得包含需要按来源模式分支解释的值。

等价性测试使用同一组手工推导样本、同一虚拟采样时钟和同一故障时间线分别驱动本机适配器与 Helper 临时服务器，比较完整规范化帧而不是比较内部实现。覆盖正常值、重复值、缺失、非有限值、陈旧、设备/Helper 断线、恢复后的新值、重复帧和帧缺口。

前端和 API 可以向后兼容地展示 `real_acquisition_mode` 与模式专属诊断，但不能用来源模式决定数值、单位、质量、保存结构或完成条件。

### 5. 共同的持久化、恢复和停止收尾

两种模式在统一帧之后复用同一持久化和生命周期核心。正式真实采集在任何物理驱动打开或 Helper 启动命令前验证保存根、会话目录和最小写入能力；失败时拒绝启动。只有显式工程预览可无保存运行，并持续报告原因、内存上限和 `production_conclusion_enabled=false`。

文件写入使用有界队列；统一帧生成不逐帧同步 flush。队列水位和高水位可观察，正式模式溢出失败关闭并保留已写证据。CSV、质量侧车、服务器捕获日志和可选 MySQL 均以统一帧身份对账；保存失败不得静默继续为正常运行。

停止状态统一为 `stopping_sampling`、`draining_transport`、`draining_writer`、`finalizing_files`、`syncing_database`、`reconciling`、`completed` 或 `failed`。`local_direct` 在停止采样阶段关闭本机驱动；`remote_helper` 先停止远程采样并完成 ACK/补传。随后两者进入相同的写入排空、文件终结、数据库同步和对账。每阶段有超时并保留“本地已保存、数据库待重试、阻塞设备/Helper、整体未完成”等并行事实。

### 6. 集成与现场证据边界

Harness 使用稳定需求 ID 分为：模式/共享合同、协议夹具、进程与传输集成、持久化/恢复、隔离装配和既有回归。新增合同测试必须先在当前矩阵或实现上以预期原因失败，随后才修改 Harness 配置、需求映射、检查入口和报告语义。

Harness 至少证明：两种显式模式存在且不可混用；统一帧和质量合同共享；相同输入产生等价规范化帧；`local_direct` 不依赖 Helper；`remote_helper` 不能绕过 readiness 与能力协商；无现场硬件证据时始终 `field_pending`；正式 `delivery` 检查前后摘要完全一致。

无硬件集成可使用模拟驱动、本机短生命周期 TCP/WebSocket/HTTP 服务器、确定性时钟和故障注入。它们的证据等级只能是 `automated` 或 `protocol_simulation`。PLC、ABB、SMRF、UVC、M3232 的物理接线/驱动/时序，以及 `remote_helper` 跨第二台 Windows 电脑的网络、权限、防火墙、睡眠恢复和长时间运行，必须保留为 `field_pending`。

## Risks / Trade-offs

- [现有 `acquisition_mode` 已区分真实与模拟] → 新增正交 `real_acquisition_mode`，不复用旧字段，避免破坏模拟兼容和语义混淆。
- [现有本地与远程路径可能都直接操作 rows/timestamps] → 先用测试锁定兼容投影，再把统一帧设为唯一新链路输入，避免一次性重写消费者。
- [Helper 旧批次缺少完整质量] → 通过能力协商在正式模式失败关闭；只允许显式工程降级，且不形成完整采集证据。
- [严格配置校验可能暴露旧调用方的隐式选择] → 对模拟调用保留兼容；真实调用必须显式迁移，并用清晰错误指出缺失或冲突字段。
- [驱动/网络恢复与统一质量之间容易重复判定] → 适配层只报告连接和样本事实，质量决策只在共享核心执行。
- [完整回归耗时较长] → 先运行每个 RED→GREEN 的窄测试，再运行相关套件，最终运行全部 Harness 与 quick/full；任何既有失败单独报告。

## Migration Plan

1. 修订并严格校验 OpenSpec，明确共享核心、两个适配层、等价性与现场边界。
2. 先增加会失败的 Harness 合同测试，记录失败原因，再最小更新矩阵、需求映射、检查入口和报告语义。
3. 以 TDD 增加显式模式配置和共享统一帧核心，保留旧字段兼容投影。
4. 以 TDD 分别实现 `local_direct` 与 `remote_helper` 适配边界，不复制共享质量、通道或保存逻辑。
5. 以同一夹具验证两种模式输出等价，并完成共同持久化、恢复、停止和错误映射。
6. 运行协议模拟、无硬件集成、相关既有回归、quick/full、OpenSpec 严格校验、语法/导入和补丁检查；正式 `delivery` 摘要必须不变。
7. 软件准备通过后，只把真实传感器及第二台 Windows 电脑确实依赖项保留为 `field_pending`；正式 delivery 更新仍需独立发布动作。
