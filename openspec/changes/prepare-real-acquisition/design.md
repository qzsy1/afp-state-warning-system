# Design

## Context

参见 [proposal.md](proposal.md) 的动机。当前仓库同时存在权威业务目录 `visualization_app/`、装配脚本、已生成 delivery 和三级回归 Harness；工作区已有大量未提交修改。当前装配脚本从 `visualization_app/` 复制显式文件集合，但现有 delivery 还包含无法由该集合稳定重建的真实采集实现。helper 的硬件检查在一次性子进程中运行，启动却由主进程代理执行；采集行和远程批次尚未使用同一逐帧质量包络。现有 Harness 又直接执行当前 delivery 中的测试，因此可能验证一个无法由权威源重建的状态。

实现必须遵守以下约束：

- 不直接修改或重新生成现有 `delivery/`。
- 不覆盖工作区已有用户修改，不执行破坏性 Git 操作。
- 保持仿真、现有10 Hz正常采集、公开API和前端字段兼容。
- 自动测试只能证明软件合同，不能代替G1–G5现场证据。

## Goals / Non-Goals

**Goals:**

- 让所有第一阶段修复存在于权威源，并能在隔离临时目录装配复现。
- 用生产路径测试协议、helper进程边界、正式保存、逐帧质量和模型采样语义。
- 让故障以明确状态失败关闭，避免“运行中但未保存”或“有数值但不可用”被解释为正常。
- 将新增检查加入现有quick/full/release矩阵，并用既有回归保护原功能。

**Non-Goals:**

- 本阶段不写入、覆盖或发布正式delivery。
- 不宣称PLC、ABB、SMRF、UVC或M3232已通过实物验收。
- 不完成第二台Windows电脑、公网、目标MySQL或真实标签G1–G5验收。
- 不重写现有采集系统，也不顺带重构与第一阶段无关的页面和训练代码。

## Decisions

### 1. 权威源优先，delivery只作为只读基线

所有产品改动进入 `visualization_app/`；装配逻辑进入 `modular_runtime/`；验证逻辑进入 `harness/`。现有 delivery 仅用于只读兼容回归和摘要比对。Harness 使用临时目录调用装配脚本，并在运行前后计算正式 delivery 受管文件摘要，断言没有变化。

选择该方案而不是直接修 delivery，是因为后者无法抵抗下一次装配覆盖。也不采用一次性把整个 delivery 反向复制回源目录的做法；该做法会覆盖当前权威源中的并行修复。需要回迁的行为将按测试逐项移入权威源。

### 2. Harness以稳定需求ID组织四层检查

新增 `REAL_PREP_SOURCE-*`、`REAL_PREP_PROTOCOL-*`、`REAL_PREP_TRANSPORT-*`、`REAL_PREP_MODEL-*`、`REAL_PREP_PERSISTENCE-*` 和 `REAL_PREP_RECOVERY-*` 需求ID，并映射到四层检查：

1. 协议与数据合同：生产解析器、采样契约、质量和保存门禁。
2. 进程与传输集成：实际helper调度器、隔离检查执行边界、批次与ACK。
3. 隔离装配：临时目标、导入、manifest和正式delivery不变性。
4. 完整回归：现有仿真、前端、helper、持久化、诊断和模型测试。

协议测试使用受控字节流或本机短生命周期服务器执行生产解析路径，不用整体替换驱动来伪造通过。无硬件检查在报告中保持 `automated` 或 `protocol_simulation`，现场项继续为 `field_pending`。

### 3. readiness使用可导入快照而不是重复打开硬件

隔离检查子进程返回结构化 `ReadinessSnapshot`：规范化配置指纹、设备身份摘要、检查开始/结束时间、有效期、接口结果和通道结果。helper主进程在把结果返回服务器前，先调用采集代理的快照导入边界；正式启动仍由主进程重新验证指纹、身份和有效期。

不选择“启动时在主进程重新检查”，因为它会再次占用USB、串口、DLL和控制器连接，可能产生检查成功但第二次打开失败的竞争。HTTP与WebSocket调度必须调用同一导入和启动边界。

### 4. Modbus TCP解析严格按请求关联

请求保存当前事务ID、协议ID和Unit ID。解析先读取7字节MBAP，其中长度字段包含已读取的Unit ID，因此后续只读取 `length - 1` 字节。随后验证事务、协议、Unit ID、功能码、异常码、字节数和请求寄存器数量；任何不一致都抛出可诊断协议错误，不返回部分寄存器。

该解析边界独立于真实套接字连接，允许夹具验证分片读取、短读、超读风险、异常响应和连续两帧边界。

### 5. 正式保存默认失败关闭

在采集配置中加入向后兼容的明确持久化策略，默认正式真实采集要求本地持久化。启动在打开物理驱动前完成保存根、会话目录和探针文件验证，失败时不创建采集线程。只有授权调用方显式选择工程无保存策略时才允许内存运行；状态始终包含策略、原因、内存边界和 `production_conclusion_enabled=false`。

模拟流程保持现有兼容行为，但当它被用于正式链路验证时同样可以选择严格持久化策略。

### 6. 统一不可变帧包络贯穿本地和远程

采集核心维护与数值行等长的帧元数据序列。对外流式接口返回不可变帧包络，包含 `capture_uuid`、绝对 `frame_sequence`、帧时间、数值、逐通道来源时间、年龄、质量和是否新值。兼容调用仍可读取旧的 `rows` 与 `timestamps`，但正式helper能力协商要求新包络。

helper、WebSocket和服务器镜像按 `capture_uuid + frame_sequence` 去重、检测缺口并保留质量。重传相同帧是幂等的；同一键内容不同则报告冲突并使正式对账失败。

### 7. 模型频率转换与质量判定集中在模型输入边界

检查点元数据新增并强制验证 `schema_version`、`sampling_hz`、通道单位、`seq_len`、`pred_len` 和 `resample_policy`。旧内置模型通过受版本控制的伴随元数据声明现有10 Hz合同，不从运行采样率猜测。

模型输入构建器接收统一帧包络：

- 输入与模型均为10 Hz时直接映射连续完整帧。
- 50 Hz到10 Hz使用严格因果、右边界封闭的5点窗口；只使用目标时刻及之前数据，不前视。
- 任何必需通道缺失、无效、陈旧、时间超限或帧不连续时，该模型点/窗口不可用。
- 断线后从新的连续段重新积累24点。

实时预测和历史预警都复用这一资格判定，不再分别只检查有限数值。

### 8. 预测可用性与生产权限分开

模型运行状态分为不可用、`available_shadow` 和 `approved_production`。默认以及没有真实标签审批文件时均为 `available_shadow`。批准证据绑定模型摘要、元数据摘要、适用工况、审批人和时间；任一摘要变化立即失效。

第一阶段只实现影子模式的安全默认与证据验证边界，不生成任何生产批准。现有 `production_conclusion_enabled` 将由该权限与采集质量共同决定，不再仅依据是否降级工程模式。

### 9. 驱动、写入和停止采用彼此隔离的有限状态

每个设备档声明最小轮询间隔、单次超时、连续失败阈值和退避上限。读取线程捕获可恢复异常后关闭、退避、重开并更新状态；不可恢复错误停止该接口但不阻塞其他接口。正式启动等待必需接口进入已打开/首帧状态或明确失败。

文件输出使用有界写入队列，帧线程不逐帧同步flush。高水位可观察；溢出时正式模式失败关闭并保留已写证据。停止状态依次为 `stopping_sampling`、`draining_writer`、`finalizing_files`、`syncing_database`、`reconciling`、`completed` 或 `failed`。每阶段有超时和具体错误，不把本地已保存与数据库已同步混成一个布尔值。

### 10. 采用测试驱动的小步迁移

每项产品行为先在权威源测试中复现失败，再做最小修复。Harness合同测试先锁定矩阵配置和临时装配不变性。单项测试变绿后运行相关测试组，最终运行quick、full、OpenSpec严格校验和工作区差异检查。现有失败必须逐项报告，不能被新增测试通过所掩盖。

## Risks / Trade-offs

- [工作区已有大量未提交改动，修改区域可能重叠] → 每个任务开始前检查目标文件差异，只做局部补丁；不还原、不批量覆盖、不直接同步整个目录。
- [第一阶段跨越采集、helper、模型和持久化，回归面较大] → 按协议、传输、持久化、模型、恢复分组完成独立红绿循环，每组后运行现有相关套件。
- [严格保存门禁可能改变旧调用方的无路径行为] → 仅对真实正式策略默认失败关闭，兼容模拟和显式工程策略，并增加旧调用回归。
- [旧helper不理解帧包络] → 通过能力协商失败关闭正式远程模式，保留明确工程降级而不静默丢质量。
- [50→10 Hz聚合会引入算法选择] → 固定版本化因果策略并用手工推导夹具锁定边界；原始50 Hz证据不丢弃。
- [驱动重连和写入队列可能掩盖持续故障] → 状态始终暴露尝试次数、高水位、最后错误和最终失败原因；达到上限后不无限重试。
- [完整回归耗时较长] → quick只运行受影响的阻断测试，full用于交付结论；两者共享同一需求映射，避免重复维护行为测试。

## Migration Plan

1. 先增加Harness需求ID、测试入口和只读临时装配骨架，不改变产品行为。
2. 依次迁移并修复Modbus解析、readiness快照、正式保存门禁和逐帧包络，每步保持旧字段兼容。
3. 增加模型元数据、因果重采样、统一质量窗口和影子权限。
4. 增加驱动重连、轮询下限、写入队列和停止状态机。
5. 运行权威源测试、quick、full和隔离装配验证；正式delivery摘要必须不变。
6. 若任一步引起不可接受回归，回退该任务的局部源补丁和矩阵项；不通过修改delivery规避问题。
7. 第一阶段通过后，G1–G5仍按现场计划逐级执行，正式发布产物更新另行审批。
