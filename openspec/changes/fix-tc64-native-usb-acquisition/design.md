# Design

## Context

动机与范围见 `proposal.md`。外部参考根目录为：

`D:\software\上位机\本机上机调试资料包-20260909\02-源程序\2-源码\运行版-无硬件模拟`

其中 `Automatic_placement_system` 是 .NET Framework 4.8 WinForms 综合上位机，含 PLC、相机、机器人、模拟数据及热电偶模块；目录名称不能证明某条链路为真实采集或模拟。热电偶实时监控实际实例化串口传输和 Modbus 服务，模拟过程数据有独立服务。

### 参考程序的通信链路

| 源文件，相对于参考项目 | 已确认的行为 | 集成边界 |
| --- | --- | --- |
| `Services/ThermocoupleModbusService.cs` | 默认 COM2、115200、地址 1、64 路，读写超时 280 ms；逐通道发送 FC03，寄存器地址为 `18 + (CH - 1) × 20`，数量 2；正常响应 9 字节 | 复用短请求、CRC16 和低字在前 float32 的通信行为，COM2 不是设备身份 |
| `Services/SerialPortThermocoupleTransport.cs` | 8N1；串口关闭后销毁旧对象，下次创建新对象并打开 | 在 AFP 现有适配器生命周期中实现，不引入 .NET 运行依赖 |
| `Services/ThermocouplePollingService.cs` | 互斥扫描，完成后安排下一轮，统计超时、CRC 与恢复；接收时间取扫描完成时刻 | 保留互斥与完成时刻；其 Start 参数不决定扫描间隔，不能按调用处的 1 秒宣称实际采样率 |
| `Services/ThermocoupleCsvLogger.cs` | 每通道保存温度、质量、请求和响应十六进制 | 复用报文诊断能力，业务数据沿用 AFP 保存合同和 D 盘路径 |
| `Models/ThermocoupleSnapshot.cs`、`ThermocoupleChannelReading.cs` | 快照含通道列表，任一有效读数即可使连接成立 | AFP 仍要求一轮完整扫描，不能据任一通道有效发布半轮数据 |
| `Form1.cs` | 实时监控连接上述服务，扫描 CH1～CH64，质量最大年龄 5 秒；日志位于程序 Logs 下 | 不移植其他设备界面、固定目录、固定 COM 号或固定新鲜度 |

参考实现的限制也需明确：CH1 普通无效即结束扫描；固定读取 9 字节，不能及时处理 5/6 字节异常帧；读取返回零字节时缺少整体截止保护；未检查 NaN/Inf、单位、输入类型及通道开关；以字符串判断传输故障；结果四舍五入至三位。上述行为不作为 AFP 的业务规则。

### 报文依据

参考项目附带 `bin/Debug/Logs/thermocouple_realtime_20260910.csv`。文件含 33,472 条记录，按时间戳分为 523 组，每组 64 路；全部行标记 Good，原始请求和响应的 CRC、地址公式、长度和字序均可相互校验。以下常量可直接作为独立协议回归依据，不要求运行时保留外部目录或复制整份 CSV。

| 通道 | 请求 | 响应 | CSV 温度 |
| --- | --- | --- | --- |
| CH1 | `01 03 00 12 00 02 64 0E` | `01 03 04 64 2B 41 FB E4 D8` | 31.424 |
| CH8 | `01 03 00 9E 00 02 A5 E5` | `01 03 04 1E 6F 41 FA 7C 15` | 31.265 |
| CH9 | `01 03 00 B2 00 02 64 2C` | `01 03 04 A4 3D 41 FB 39 1C` | 31.455 |
| CH56 | `01 03 04 5E 00 02 A4 E9` | `01 03 04 6C 28 41 F8 56 B9` | 31.053 |
| CH57 | `01 03 04 72 00 02 65 20` | `01 03 04 6A 28 41 FD 96 32` | 31.677 |
| CH64 | `01 03 04 FE 00 02 A4 CB` | `01 03 04 52 C3 41 FB 6B 64` | 31.415 |

响应数据 `64 2B 41 FB` 按每寄存器高字节在前、低 16 位字在前解码，与 CSV 差值不超过其三位小数舍入误差 0.0005。报文常量证明实现和附带文件一致，不能证明文件来源、当前实物、USB 接口身份或当前仪表设置。

### AFP 当前接入位置

- `visualization_app/hp_thermocouple64.py` 已实现 FC03、CRC、两种异常帧、单位及输入类型和通道开关检查；每通道 20 寄存器，单次读 6 通道的 120 寄存器，最后 80 寄存器，共 11 次请求。首轮完整扫描在 open 时执行；失败轮次不发布。
- 参考程序与 AFP 的温度寄存器和字序一致。关键差异是请求地址范围、响应长度和扫描节奏；尚无当前设备实测证明批量读取就是通信失败根因。
- `acquisition.py` 的串口、注册表降级及占位目录的 `compatible_roles` 缺少 `thermocouple64`；`local_capture_agent.py` 用设备驱动名匹配传输的 `protocol=serial`，无法选出对应串口。
- `static/app.js` 的热电偶自动分配会按候选排序选取端点；`physical_verified` 表示物理发现，不能代替协议和数据验证。`thermocouple_reachable` 仍取旧 HID 枚举结果。
- `MultiInterfaceDriver` 和单接口工厂负责构造驱动；`LocalDirectAdapter` 负责采集互斥、缓存发布及重连。启动等待使用驱动的 `open_timeout_seconds`，当前 TC64 最小轮询间隔 0.1 秒、默认新鲜度 1 秒，均需结合逐通道扫描实测验证。
- `pre_sensor_config.py` 的方案持久化字段白名单，以及配置加载、前端配置往返、Helper 和 `real_acquisition.py` 的就绪指纹，需要覆盖新增配置，否则重启可能丢失读取方式或沿用旧验证。
- `test_hp_thermocouple64.py` 的 11 次请求断言仅覆盖现有批量模式，应保留为显式模式的回归。主规格库尚为空；当前热电偶的设备角色、驱动和通道数量以本变更及 `expand-thermocouple-to-64-channels` 为准，远端传输复用 `fix-remote-acquisition-workflows` 的 Helper 合同，通道、分组和补值遵守六十四路变更合同。

## Goals / Non-Goals

**Goals:**

- 将参考程序已明确的短请求采集方式整合进现有 Python 驱动和端到端采集链路，形成可复现的报文依据。
- 让接口发现、设备绑定、协议有效和温度有效具有各自的证据，最终在实际原生 USB 接线上验证采集。
- 保持 64 路原始通道、八组派生均值、统一帧和保存合同；提高异常帧、扫描中断和重连的可诊断性。

**Non-Goals:**

- 不复制或启动整套外部上位机，不移植 PLC、机器人、相机、UI 和模拟器，不增加 .NET 或厂商 SDK 依赖。
- 不自动修改仪表模式、地址、单位、补偿、通道开关或驱动绑定；不将 RS232 转接线替代原生 USB 验收。
- 不据参考 CSV 或协议夹具宣称当前实物通过，不将未知有限高温直接定义为探头断线。

## Decisions

### 1. 在现有驱动内显式选择读取方式

保留驱动标识 `huipu_tc64_modbus_rtu`，新增 `read_profile`：

- `channel_temperature`：默认兼容方式，依次 CH1～CH64，每个温度请求只读 2 个寄存器，正常响应 9 字节。
- `full_record_block`：显式保留现有 11 次完整记录读取方式及其解析检查，用于已经验证该方式的设备。

新增配置及未包含该字段的配置统一规范化为默认兼容方式，规范化后的方式进入就绪指纹，既有检查结论失效。用户明确保存的方式往返保持，非法值拒绝。失败时不静默切换方式，不进行全端口或全地址盲扫；现场可显式对比两种方式的收发记录。采用同一驱动可复用生命周期与数据合同，无需第二套独立应用或重复驱动标识。

### 2. 复用通用 RTU 收发，独立解码温度

逐通道方式使用同一 CRC、地址、功能码和字节数检查，按响应头接收正常帧或 5/6 字节异常帧；支持分片到达，拒绝错误帧、额外数据和跨请求残留。串口使用非阻塞读取，高分辨率单调时钟控制单请求截止、整轮截止及完整帧后的显式静默窗口，避免 Windows 粗粒度时钟或串口通用超时被逐事务累加；请求和响应的线速均计入预算。保留帧间间隔、扫描取消和停机释放能力。

温度 float32 解码与完整记录质量判断分离；逐通道读取不得伪造 20 寄存器元数据。内部保留原始精度，显示及导出按 AFP 既有规则格式化，不在驱动层强制三位舍入。依据上表独立字节常量测试，不能只用新实现生成自己的期望值。

### 3. 单位与通道设置必须有来源

两寄存器温度响应不包含单位、输入类型或通道开关。连接验证时以小范围只读 FC03 获取每通道偏移 1～2 的单位和输入类型，以及偏移 14 的开关；不依赖原先 120 寄存器请求来完成兼容路径的前置验证。首轮全部设置和温度通过后，驱动在当前连接内缓存有来源的设置，常规轮只执行 64 个温度请求；关闭、重连或配置变化立即清除缓存并重新验证。完整记录模式继续使用自身元数据。

若仪表明确拒绝上述元数据读取，允许操作者依据仪表实际设置确认对应通道的单位、温度输入和启用状态，确认随设备绑定及配置保存，并在页面显示其来源。未读到且未确认的项保持未知，相应通道不得作为有效摄氏温度发布；不得默认为摄氏度或已启用。开关、类型或单位变化后重新检查；连接恢复重新读回，人工确认须针对相同设备及实际设置复核。无响应、CRC 错误等通信失败不能自动转为人工确认成功。

复用现有摄氏/开尔文/华氏转换和非温度输入排除；NaN/Inf、关闭通道和已有依据的故障状态输出 null 与原因。没有依据的有限哨兵值保留待核实，不擅自扩大故障规则。

### 4. 全轮发布和单通道无效分别处理

数据阶段依次处理 64 个温度响应；有效协议下的通道关闭、非有限温度或已知探头异常只使对应通道无效，不能因 CH1 无效跳过 CH2～CH64。任一温度事务发生超时、CRC、地址或帧结构错误时废弃该轮，撤销协议验证并交给现有适配器关闭及重连，不能复用失效串口对象。

完整协议扫描才更新观测序号和扫描完成接收时刻；全轮通道均无效仍可报告协议有响应，但不能报告已取得有效温度。扫描期间的各通道并非同时采样，记录扫描起止及耗时，不以页面刷新频率宣称仪表同频采样。

### 5. 发现候选、确认身份与恢复绑定分开

所有真实和降级串口目录统一描述传输能力；Helper 依据 `kind=serial`、`protocol=serial` 和角色候选匹配，设备驱动单独配置。前端不能按 COM 排序、CH340/FTDI VID/PID 或 USB 位置单独确认热电偶；多候选保持待明确选择，保留用户停用状态及手动绑定，并排除其他角色已占用资源。

接口归属通过操作者确认的实际接线、拔插枚举差异及协议温度对照建立。COM2 仅是外部程序默认值；现有方案中的 COM5/COM6 也不能直接继承为当前仪表身份。没有枚举变化时检查数据线、通信 USB 口、电脑直连口和仪表模式；未知设备按其硬件 ID 判断驱动需要，不重装正常设备驱动作为默认措施。

有稳定设备身份时可恢复同一设备的新 COM；无法建立唯一对应时要求重新选择。改变物理身份、端点、波特率、从站地址、读取方式、通道设置或启用状态均使旧验证失效。物理发现、协议响应与有效温度分别展示，修正旧 HID 状态的使用方。

### 6. 将诊断和配置贯通全部入口

`read_profile`、超时和有来源的通道设置贯穿配置规范化、两个驱动工厂、连接检查、Helper、前端表单与方案保存、管理员方案白名单及现场配置文件加载；校验后的有效配置进入就绪指纹。保存配置不能保存可复用的采集就绪授权。

每次检查限定用户选中的端点和实际参数，呈现打开结果、读取方式、地址范围/通道、TX/RX 字节数、最后有界长度原始帧、整轮耗时和分类错误。沿用现有会话占用保护，不并发启动探针。原始报文诊断写入会话诊断/质量元数据和既有保存机制，不改变每帧固定通道目录，不在内存无限保存报文，也不复制参考程序的逐行 CSV 结构。

### 7. 以扫描预算驱动新鲜度和重连

启动等待预算覆盖首轮 128 次设置读取、64 次温度事务、请求与响应线速、帧间间隔及有限余量；不再沿用 11 次分块的预算。同一连接后续轮只预算 64 次温度事务。逐请求和整轮均有上界，停止请求可取消后续事务。正常轮询在完整扫描结束后安排，使用 AFP 现有互斥和退避，故障时避免立即空转。

根据实测正常完整扫描周期、元数据刷新成本和轮询间隔设置新鲜度，明确保持及过期状态，不能简单改为参考程序固定 5 秒。重连窗口应覆盖 Windows USB 重新枚举的时间，不因当前默认 5 次快速重试过早终止；窗口及上界进入可测试配置，不影响其他驱动。重连成功必须重新验证整轮后才发布新温度。

### 8. 验收围绕原生 USB、温度变化和保存一致性

自动化测试使用参考报文常量及只支持 2 寄存器温度请求的模拟串口证明默认兼容模式无需大范围温度读取；元数据以独立小请求覆盖。完整记录模式保留现有回归。候选、参数持久化、前端、Helper、真实采集缓存、统一帧、CSV/MySQL 与远端传输分别验证对应合同。

现场先确认 USB 设备和仪表设置，关闭占用端口的软件，以 AFP 显式选择接口启动。若零响应，对照参考程序的只读请求和实际模式/地址逐项定位；只有已确认该 USB 无法使用参考协议时再获取 PC 协议或 SDK，缺少依据时报告具体阻塞，不将其作为软件兼容路径开发的前置条件。

逐路或分组激励全部 64 路，重点核对 CH1/8/9/56/57/64 的映射，并与仪表显示或依次运行的参考软件比较。比较采用仪表分辨率、精度和扫描时间差形成的容差，不能将 CSV 的 0.0005 舍入差当作实物精度。至少 10 分钟持续采集、单通道异常、USB 断开/恢复以及已启用保存目标对账通过后，才可标记设备验收通过；未接通道明确无效，不虚构 64 路有效温度。

## Risks / Trade-offs

- [短温度请求仍可能无响应] → 参考资料只证明协议实现，实际线缆、端口、模式和地址由现场读回验证；不预先断言批量请求为根因。
- [元数据未包含在温度响应中] → 使用小范围读回或针对实际仪表的明确设置确认；未知质量不冒充已测摄氏温度。
- [64 次读取延长扫描与故障预算] → 测量实际周期，设置整轮上界、取消、退避和适配器等待预算；不承诺固定硬件采样率。
- [通用 USB 串口缺少稳定序列号] → 保留绑定来源，使用物理对应和温度激励验证；身份不确定时禁止静默重绑。
- [参考源码/附带数据来源无法单凭文件验证] → 将其用作兼容性依据和协议夹具，独立完成当前设备实测。
- [参考软件或其他角色占用串口] → 分时比较、显式资源冲突检查；不主动关闭未知用户进程。
- [源码与运行目录行为可能不同] → 软件回归与获准发布后的固定目录复验分别核对。

## Migration Plan

在固定源码目录的本机任务分支完成实施，不修改外部参考包，不复制项目或创建 worktree。先落地参考报文回归、逐通道兼容路径和配置，再贯通发现、验证、缓存与保存；硬件缺席不阻止软件实现和夹具测试，但现场验收任务保持未完成。既有资料与状态说明直接更新原文件，仅描述有效行为。

获得明确发布授权后，使用现有单运行目录流程；中间产物仅放 `D:\AFP_Runtime\.afp-staging`，发布成功或失败均清理。更新 `D:\AFP_Runtime\AFP_Integrated_System_Modular` 并从该目录启动，核对交付版本、磁盘摘要、进程路径、运行修订及页面资源，重复识别、温度更新和保存检查；回退沿用受控流程，不长期保留完整候选副本。

采集默认写入已确认存在且可写的 `D:\AFP_Capture`。软件更新与设备最终验收分别报告；未获发布授权时说明正式目录未更新，未取得实物证据时不能标记设备通过。
