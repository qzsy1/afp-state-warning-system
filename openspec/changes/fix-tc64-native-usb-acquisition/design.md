# Design

## Context

动机见 `proposal.md`。当前有效的诊断依据如下，均不等同于仪表型号确认或硬件验收：

资料来源为 `D:\keti\自动铺丝\数据采集相关` 中 10 月保存的 `热电偶采集仪协议.pdf`、`（常规）5寸40-64多功能TCP多路温度记录仪说明书慧谱(1)(1).docx`、`HpTemperatureLogger_CN_V1.2.zip` 和 `USB下载口驱动程序CH340.exe`。10 月说明书与同目录较早的 `(1).docx` 摘要一致。商家 ZIP 只有安装 EXE，现有解包主程序 `TemperatureLogger.exe` 使用 Qt SerialPort；这些材料未提供可直接集成的 SDK 或独立 USB 协议文件。CH340 已正常枚举，不以重装驱动为默认修复措施。

现有实现的明确缺口：

- `acquisition.py` 的真实枚举、注册表降级和串口占位项的 `compatible_roles` 不含 `thermocouple64`。前端实际上仅按串口类型筛选，遗漏元数据不等于页面不显示某个串口；需统一合同而非仅补字符串。
- `static/app.js` 的自动分配可将任意串口当作热电偶候选。以实际串口和 USB 端口目录复现时，未指定绑定的热电偶被选为 COM6，并获得 `physical_verified=true`；这只是传输发现，未经过 TCP64 协议验证。该复现不能证明现存配置的全部形成过程。
- `local_capture_agent.py` 的 `_ROLE_SPECS` 使用驱动名 `huipu_tc64_modbus_rtu` 匹配传输的 `protocol`，但枚举值为 `serial`；在相同发现结果下 `_choose_candidate` 返回空。
- `thermocouple_reachable` 仍依据旧 HID 枚举计算，不能用于 TCP64 的协议可达性。
- 正式目录和源码的慧谱驱动摘要相同；`acquisition.py`、`static/app.js` 摘要不同。不能将源码检查直接当作正式程序行为证明，验收须同时核对已加载资源。

## Goals / Non-Goals

**Goals:**

- 在现有传输目录和采集架构中修复 TCP64 的候选绑定、协议验证和诊断，使原生 USB 的可用性有实际读回依据。
- 先解决无响应的前置条件，再验证完整 64 路，不将协议夹具通过当作设备连通。

**Non-Goals:**

- 不改写既有六十四路目录、八组均值、跨层补齐及模型语义。
- 不自动更改仪表模式、地址、通道配置、补偿和报警，不恢复出厂设置。
- 不把 RS232/RS485 转接接线作为原生 USB 验收替代品；若该 USB 通路无法支持，明确报告阻塞并另行确认接线范围。

## Decisions

1. **分离传输能力与设备身份。** 串口项使用 `kind=serial`、`protocol=serial` 表达传输，通过角色候选和驱动配置表达 TCP64 协议。核心、页面和 Helper 共享角色匹配语义；不能把物理传输的 `protocol` 全部重命名为某个设备驱动。候选元数据补全覆盖真实枚举及降级路径，CH340 不独占归属热电偶或 ESR1001。

2. **不使用枚举顺序确认设备。** 多候选且身份未知时提供选择；有用户确认的绑定或可验证身份才允许自动恢复。无序列号的 CH340 结合 PnP、物理位置和重新协议验证处理，COM 号或换插口不能独自继承验证。保持 `physical_verified` 的物理发现含义，单列协议和数据证据；保留停用状态，防止发现操作自动打开接口。旧自动绑定只降级其验证结论，不静默覆盖用户配置。

3. **先定位物理设备，再选择协议。** 使用独立拔下并保持断开、重新插入后的完整 PnP 差异，确认热电偶对应的设备；仅见通用串口或 COM 号变化不能确认归属。无枚举变化时核对仪表数据通信 USB 口、可传数据的线缆、直连电脑端口及仪表 USB 模式；若有未知设备再根据硬件 ID 检查驱动，不盲目重装正常设备的驱动。物理对应成立后读取仪表设置，使用商家上位机单独读取型号、通道数和温度，退出后再测 AFP。需要切换仪表设置时由操作者明确操作。公开 PDF 的 RS232 约束不能直接外推至 USB，需向厂商确认 USB 的模式适用范围、握手及帧格式。USB 返回合法 Modbus 响应时复用 `HpThermocouple64Driver`；确认仅支持 PC 模式时，取得协议/SDK和可复现报文后接入独立适配器。缺少依据时保持具体阻塞，不猜测报文。

4. **检查过程有界且只读。** 正常检查只访问用户选中的接口，带实际地址、波特率、请求范围、收发计数、耗时和错误分类；不全端口全地址盲扫。输出区分 `port_missing`、`port_busy`、`no_response`、`protocol_mismatch`、校验失败和通道无效。无响应提示列出待核对项，不推断仪表损坏；有真实会话时沿用既有占用保护。

5. **完整扫描后才发布。** Modbus 路径复用现有 11 次分块及低字在前 float32 解码，不改变已有验证通过的寄存器模型。PC 路径必须验证同样的 64 路规范输出。新鲜度以完整扫描实测耗时配置；只有完整新扫描更新观测序号和接收时刻。对有限故障哨兵必须获得厂商或实测依据，不能擅自将高温值定义为断线。

6. **验收以真实行为为准。** 测试覆盖 COM6/COM7 同时存在、排序改变、蓝牙串口、停用恢复、Helper 候选和配置变动后验证失效。现场按 CH1/8/9/56/57/64 边界及全部通道进行激励映射检查，验证探头异常、USB 断开恢复及 CSV/MySQL 与页面对账。持续采集至少 10 分钟并记录完整扫描耗时、有效率和错误计数；预期未接探头明确标为无效，不要求虚构 64 个有效温度。

## Risks / Trade-offs

- [实际 USB 协议未确认] → 以仪表设置、商家上位机和厂商协议为前置证据；无法取得时保留明确阻塞，不以串口发现修复代替采集修复。
- [串口芯片身份通用且 CH340 无序列号] → 候选只表示可能兼容；不持久相信旧 COM 号，每次设备变化撤销协议验证。
- [商家上位机与 AFP 争用串口] → 顺序进行测试，检查端口占用并关闭后再切换，避免并发探测。
- [扫描耗时超过统一帧周期] → 按实际设备刷新速度设置新鲜度，保持值和过期值显式标记，不据统一帧频率宣称硬件同频采样。
- [源码与正式目录不完全一致] → 分别检查源码回归和正式运行行为；获得发布授权后再更新固定目录并复验。

## Migration Plan

在当前单 checkout 的本机任务分支完成修复，先完成协议前置验证及定向回归，再运行与改动范围对应的 Harness 检查。与其他未提交修改分开核验，不替换未知来源配置。

发布前取得明确授权；构建中间产物仅写 `D:\AFP_Runtime\.afp-staging`，通过既有单运行目录流程更新 `D:\AFP_Runtime\AFP_Integrated_System_Modular`，启动后核对清单摘要、进程路径、运行修订和页面资源。发布失败时通过既有受控回退恢复，不长期保留完整候选副本；成功或失败均清理 staging。软件更新与设备实物验收分别报告。当前规划不授权实施或发布。
