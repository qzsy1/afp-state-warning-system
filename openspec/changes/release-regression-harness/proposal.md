## Why

项目已形成模拟/真实采集、边缘辅助程序、CSV/MySQL、局域网/公网、WebSocket、本地规则与模型增强诊断等多条相互关联的业务链路。过去按单点问题修改时，容易出现新问题修复后既有正常功能回退，因此需要把核心能力、回归范围和发布条件固化为可执行且不可绕过的质量门禁。

同时，当前软件采用稳定启动器 EXE 加外部业务代码的结构，多数修改不需要重新生成 EXE。质量门禁必须默认复用已有 EXE，并在未触发明确重建条件时强制保持其哈希不变。

## What Changes

- 建立核心功能回归基线，覆盖启动、模拟采集、真实采集状态、传感器与接口映射、边缘辅助程序、CSV/MySQL、诊断、局域网/公网、WebSocket和17通道/薄膜压力通道。
- 建立三级质量门禁：开发快速检查、合并完整回归、发布交付验收。
- 将Harness集中到仓库根目录的独立 `harness/` 文件夹，并为原回归矩阵中的每个检查项提供可直接双击的独立 `.cmd` 入口。
- 为quick、full和release三种配置提供可直接双击的组合入口；所有入口复用同一套声明式矩阵与执行引擎，不在批处理文件中复制检查逻辑。
- 建立需求编号与测试命令之间的可追踪矩阵，并生成机器可读和人工可读报告。
- 增加运行环境预检、Python/Node/EXE错误分类和源码文件/行号提取；仅在存在失败、环境缺失或现场待验证事项时生成并打开错误报告。
- 任一必需检查失败时，Harness MUST 返回非零退出码；发布门禁失败时 MUST 阻止稳定标签和交付发布。
- 建立自动EXE重建判定。普通Python、HTML、CSS、JavaScript、SQL、配置、模型和文档修改 MUST 复用原EXE。
- 将启动器二进制构建与交付目录组装拆分为独立脚本；只有启动器构建边界变化才触发EXE重建，外置文件、配置和校验清单组装变化 MUST 默认复用稳定EXE。
- 未触发重建条件时，Harness MUST 校验发布前后EXE的SHA-256完全一致。
- 只有运行时、启动器、原生依赖或模块API不兼容变化等明确条件才允许重建EXE，并要求记录原因和完整验证证据。
- 区分自动化验证、本机集成验证和现场硬件验证；没有真实硬件证据时不得宣称现场采集通过。
- 增加GitHub质量检查入口，使稳定分支可以配置为质量门禁未通过时禁止合并。

## Capabilities

### New Capabilities

- `core-regression-baseline`: 定义每次变更都不得破坏的核心业务能力、验证层级和未验证边界。
- `release-regression-gate`: 定义三级Harness、需求测试追踪、失败阻断、报告和GitHub合并/发布门禁。
- `stable-executable-reuse`: 定义默认复用稳定EXE、重建触发条件、哈希不变性和重建审计要求。

### Modified Capabilities

无。当前仓库尚未建立OpenSpec主规格，本次新增能力规格。

## Impact

- 新增 `openspec/` 中的规格与变更工件。
- 后续实现将把统一验证入口、回归矩阵、测试配置和Harness测试集中到根目录 `harness/`，并保留旧入口作为兼容转发层。
- Windows人工检查将获得单项 `.cmd` 和quick/full/release `.cmd`，双击运行后窗口保持打开；全部通过时只显示摘要，有问题时打开仅包含问题项的HTML报告。
- 后续实现可能对现有模块化构建/发布脚本增加前置质量门禁，但不得改变现有业务行为。
- `modular_runtime/build_modular_app.ps1` 保留为兼容编排入口，分别调用启动器构建脚本和交付组装脚本，现有调用方无需立即迁移。
- 复用现有 `unittest`、模块状态、自检、文件完整性、集成冒烟和功能冒烟入口，不重复建设已有测试。
- Harness的自动化测试不能替代真实SMRF、PLC、ABB、UVC、M3232设备及真实目标MySQL的现场验收。
