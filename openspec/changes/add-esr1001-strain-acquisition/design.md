## Context

参见 `proposal.md` 的动机和 `specs/esr1001-strain-acquisition/spec.md` 的行为合同。当前采集核心在 `visualization_app/acquisition.py` 中维护数据模式、通道目录、接口档案和多接口驱动；五类实物接口各自运行并汇入统一缓存，逐层 CSV 由规范列生成，MySQL 在 `sensor_json` 中保存传感器键值。配置和现场门禁还分布在 `pre_sensor`、本机/远程 helper、Web/桌面界面、诊断工具、harness 和交付合同中。

ESR1001-A 资料确认设备有 4 个应变输入，RS485 使用标准 Modbus、默认 `9600-8-N-1` 和地址 1。当前目标目录中的 `MODBUS调试助手.exe` 是通用调试工具，不是可修改的项目源代码；可执行实现应落在本仓库。配套 `test.py` 和手册均使用 FC04 读取 `0x0030` 的 8 个寄存器，设备按 `CH4、CH1、CH2、CH3` 返回四个大端 float32。该实数寄存器要求支持 2025-11-17 版协议的设备固件。

## Goals / Non-Goals

**Goals:**

- 让一台 ESR1001-A 通过独立 RS485 串口成为第六类可发现、可配置、可诊断和可重连的逻辑接口。
- 原子采集四路微应变并在实时显示、21 通道 CSV、MySQL、回放和远程 helper 中保持同一规范名称和顺序。
- 用新的数据模式区分 21 通道数据，同时保持既有 17 通道数据和 16 输入模型可用。
- 通过协议夹具、端到端持久化对账和实物耐久测试形成可执行验收闭环。

**Non-Goals:**

- 不修改或反编译供应商的 `MODBUS调试助手.exe` 和 ESR1001-A 上位机程序。
- 不把微应变直接换算为应力；应力计算需要材料弹性模量、截面、桥路和标定合同，当前只保存设备输出的 `με`。
- 不在同一 RS485 总线上编排多台 ESR1001-A；本变更只接入一个可配置从站地址。
- 不自动改写设备增益、采样率、滤波、标定系数、设备地址或波特率。
- 不训练新模型，也不把应变通道强制加入现有预测权重。

## Decisions

### 1. 使用独立 COM 口上的 Modbus RTU，而不是 USB TTL 主动上传

物理档案定义为 `serial`，驱动定义为 `modbus_rtu_esr1001`，协议定义为 `modbus_rtu`。连接链路为电脑 USB-RS485 转换器或原生 RS485 口到设备的 485A/485B；端口必须与 M3232 分开并由稳定物理资源标识保存。

选择 RS485 是因为用户提供的目标程序、配置和示例代码均指向 Modbus 轮询，协议具有地址、长度和 CRC 边界，也便于接入现有独立工作单元和诊断链路。USB TTL 的主动上传协议没有 CRC，且会把设备内置 CH340N 串口与 RS485 部署方式混为一谈，因此不作为当前正式采集路径。

### 2. 用轻量原生 RTU 编解码器复用现有 pyserial

驱动基于已经随交付包提供的 `pyserial`：构造 RTU 请求、计算 CRC16/MODBUS、按期限读取完整响应并严格校验。无需增加 `pymodbus` 依赖，减少打包体积和依赖变动；协议面很小，测试可覆盖全部分支。

编解码器采用显式帧合同：

| 项目 | 值 |
|---|---|
| 默认串口 | 操作者选择；不得硬编码现场 COM 号 |
| 串口格式 | 9600 bit/s、8 数据位、无校验、1 停止位 |
| 默认从站 | `0x01` |
| 读取 | FC04，起始 `0x0030`，数量 8 |
| 默认请求 | `01 04 00 30 00 08 F1 C3` |
| 响应 | 地址 + FC04 + `0x10` + 16 数据字节 + CRC |
| 数值 | 每通道大端 IEEE-754 float32，单位 `με` |
| 设备顺序 | `CH4、CH1、CH2、CH3` |
| 规范顺序 | `应变1、应变2、应变3、应变4` |

读取逻辑必须处理串口分片和粘连，只在精确得到一帧并通过地址、功能码、字节数、总长、CRC 和有限值检查后发布四通道。任何失败都丢弃整帧，避免跨帧或部分通道污染统一缓存。

### 3. 驱动只管理必要的启用和启停

打开接口后，驱动确认从站可响应；需要时通过 FC06 将 `0x0015` 设为 4，并通过 FC05 将 `0x0009` 设为标准线圈开启值 `0xFF00`。设备已经自动采集时该操作保持幂等。正常关闭时尝试写 `0x0000` 停止，但保存队列收尾不依赖停止应答。

增益、采样率、滤波、标定、地址和波特率不由采集会话修改。这样避免软件启动改变计量配置。FC04 `0x0030` 返回非法地址时直接判定固件不兼容，不自动回退到 `0x0013` 整数值；整数负值说明和实数标定合同不同，静默回退会让同一通道产生两种不可区分的数据语义。

### 4. 四通道作为一个原子观测进入统一时钟

ESR1001-A 使用与其他实物驱动相同的独立工作单元、重连退避和有界缓存。一次有效响应产生四个共享源观测时间的值，统一 10 Hz 帧只读取该原子快照。建议新鲜度上限使用 0.25 秒，并记录有效帧率、超时、CRC、异常码、重连次数和最后有效时间；最终值由现场 10 Hz 负载测试确认，但不得放宽为无限复用旧值。

该设计让 9600 bit/s 下约 21 字节的响应满足 10 Hz 轮询，同时保证应变串口故障不会拖慢 PLC、ABB、热电偶、UVC 或 M3232。

### 5. 新增 `new_collection_v12_0`，不改变旧数据模式含义

新的规范通道顺序为原有 17 通道后追加 `应变1～应变4`，完整宽表为 21 个传感器通道、4 个工艺参数以及现有时间和身份列。`new_collection_v12_0` 成为包含 ESR1001-A 的新会话模式；`new_collection_v11_3` 继续严格表示 17 通道。

为旧模式改写通道数量会导致同一 `schema_id` 对应两种列合同，因此不采用。读取、回放、训练和导出均按记录中的模式选择通道目录。默认完整采集选择 21 通道；操作者仍可取消未接入的可选通道，但正式完整门禁要求 21 通道。

### 6. 采集通道与模型输入分离

新增应变数据先进入采集、实时展示和持久化，模型输入继续读取检查点元数据中的 `input_sensors`、缩放参数和维度。现有 16 输入检查点在 21 通道会话中只取声明的 16 列。只有新的模型工件完整声明应变通道并通过维度/缩放验证时，推理才可消费应变数据。

这一边界避免通道增加导致现有预测失效，也避免以零填充或截断方式掩盖模型合同错误。

### 7. CSV 增加四列，MySQL 沿用 JSON 存储

CSV 的规范列生成器和完整试样合并器按 `new_collection_v12_0` 输出四个新增列。质量侧车记录每个应变通道的观测数、缺失区间、新鲜度和协议错误，缺失值不替换为零。

MySQL 的 `afp_sensor_sample` 与 `afp_sample_all` 已使用 `sensor_json`，因此不执行表结构 ALTER；保存时按新模式把四个规范键写入 JSON，平面查询和导出再展开为四列。现有事务、主键、双表兼容、重试文件和幂等覆盖保持不变。验收同时比较 CSV 行、两个样本表、所有启用 MySQL 目标和抽样通道值，不能只比较行数。

### 8. 六接口合同贯穿本机、helper、界面和诊断

默认接口目录新增稳定 ID `esr1001_strain`，预传感器配置使用 `esr1001-strain`，并增加非敏感端点引用 `AFP_INTERFACE_ESR1001`。本机直连在采集电脑打开 COM 口；远程模式只允许 helper 打开其本机 COM 口，服务器接收规范化样本和状态。

Web/桌面界面从返回的接口和通道目录生成数量、卡片、选择项、模拟映射和状态摘要，移除只适用于五接口/17通道的硬编码。串口发现只提供候选；选择恢复优先使用已保存的稳定物理端口，未知串口不自动冒充 ESR1001-A。协议握手是最终身份依据。

诊断目录新增 ESR1001-A 规则，区分：端口不存在、被占用、串口格式错误、无响应、错误从站、CRC 错误、长度错误、Modbus 异常、固件不支持实数寄存器和数据过期。诊断保持只读；需要写入启停的检查在受控硬件探针中完成。

### 9. 验证采用三层证据但文档只维护当前验收合同

- 协议级：CRC 黄金向量、手册请求/响应、分片读取、错误地址/功能码/长度/CRC、异常响应、非有限 float、启停应答和超时。
- 系统级：6 接口与 21 通道目录、本机/远程/模拟映射、端口冲突、独立重连、CSV/MySQL/重试/导出对账、旧模式兼容和模型输入隔离。
- 实物级：确认固件支持 `0x0030`，四路接线和通道顺序正确；使用已知应变输入验证符号、量级和通道对应；六类实物以 10 Hz 联采 600 秒并完成 6000 行对账。

自动化证据不能替代实物的桥路、标定、固件和 RS485 电气验证。所有当前状态文档只描述最终有效合同，不保留临时实施阶段或已作废方案。

## Risks / Trade-offs

- [固件过旧不支持 `0x0030` 实数寄存器] → 预检读取该寄存器并给出明确升级要求，禁止静默整数回退。
- [USB-RS485 转换器没有可靠型号身份] → 保存稳定 PnP/物理端口绑定，要求协议握手确认，禁止任意串口自动认领。
- [9600 bit/s、总线周转和 Windows 调度导致有效帧率不足] → 独立轮询、期限读取、帧率指标和 600 秒实测；必要时只在设备和适配器共同验证后显式提高波特率。
- [设备通道返回顺序不直观] → 在单一映射表中固定 `CH4、CH1、CH2、CH3` 到规范顺序，并用逐通道施加载荷的现场测试确认。
- [新增列误入旧模型] → 新数据模式和模型元数据双重校验，采集列与模型列分别维护。
- [CSV 和 JSON MySQL 导出列不一致] → 共用数据模式通道目录生成列，并进行值级抽样对账。
- [应变被误称为应力] → 单位和名称固定为 `με`；没有材料与标定合同不生成 MPa 应力列。

## Migration Plan

1. 在代码和配置中同时加入 `new_collection_v12_0`、第六接口和四通道目录，保留 `new_collection_v11_3` 的解析与回放。
2. 完成 RTU 协议驱动、独立工作单元接入、物理端口选择、helper 投影和诊断，再启用 21 通道为新完整采集默认值。
3. 完成 CSV/MySQL/导出/重试对账以及 UI、harness、发布合同和交付打包更新。
4. 使用协议模拟器通过自动化门禁后，在现场确认固件、接线、通道顺序、标定和 600 秒联采。
5. 发布前保留上一份可运行交付包和配置；若新接口验收失败，回滚到上一交付包并继续读取既有 `new_collection_v11_3` 数据，不把失败的 21 通道会话标记为正式数据。
